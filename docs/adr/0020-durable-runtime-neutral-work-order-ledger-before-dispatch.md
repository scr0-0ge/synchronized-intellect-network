# Persist Runtime-neutral Work Orders and endpoint slots before Worker dispatch

Work Order acceptance, lifecycle recovery, and endpoint concurrency ownership live behind one deep local-coordinator Module. `createRuntimeWorkOrderLedger(...)` owns a private versioned SQLite table family and presents only `coordinate(...)`, `snapshot()`, and `close()`. Callers do not reproduce transaction ordering, slot accounting, idempotency, restart recovery, or malformed-state validation.

For a new Work Order, the Module first commits the bounded intent, canonical digest, idempotency key, separately supplied Supervisor binding, and an `unreserved` slot. Only then does it call the accepted Runtime Endpoint Directory authorization Interface. A successful immutable authorization is committed together with an `owned` endpoint slot in a second `BEGIN IMMEDIATE` transaction. Only a later durable effect claim can return an inert start or control intent. The Directory result adds only `endpointConcurrencyLimit`, derived from the selected endpoint's immutable policy snapshot; sanitized snapshots, private Adapter resolution, Runtime-owned authentication, and zero-effect authorization remain unchanged.

Slot ownership is monotonic: `unreserved -> owned -> released`. Authorized pre-start, start-claimed, running, control-claimed, and outcome-unknown/recovery-required records remain owned. A slot is released exactly once only after a durable fact proves that no external Worker can still consume it: safe pre-start cancellation, confirmed start failure, normal Handoff, or committed cancellation/interruption. Restart after a claimed but uncommitted external effect becomes outcome-unknown, emits no replay intent, and never frees capacity. Endpoint availability is reconstructed from durable owned slot units under the exact directory and endpoint snapshot keys, not from in-memory Worker objects or display labels.

The ledger is bound to one exact Runtime Endpoint Directory snapshot epoch. A structural preflight validates schema fingerprints and all stored relations before epoch mutation or recovery. If restart supplies a different epoch while a nonterminal or owned record survives, the Module fails closed with reconciliation required and emits no intent. A fully terminal, structurally valid epoch may be retired and replaced; its exact historical keys remain unchanged. Endpoints are never correlated by Runtime family, model label, location, or another display value. A later bounded slice may add private directory-snapshot restoration or explicit reconciliation.

The version-one schema uses seven ledger-prefixed `STRICT` tables and six fixed indexes. It does not use `PRAGMA user_version`, alter an existing schema, or accept unrelated user tables in its focused caller-supplied database. Canonical schema fingerprints, foreign keys, root/epoch/event revision bounds, Work Order and Supervisor digests, authorization/slot relations, bidirectional Worker linkage, terminal/control/Handoff state, and exact endpoint capacity are revalidated before every public operation. Public results expose only opaque ledger and exact-snapshot keys, Access Mode, lifecycle, slot summaries, fixed categories, or inert intents; raw intent and Supervisor binding remain private durable data.

Issue 30 implements this production state authority without wiring it into Electron, the Workbench, or the current Project Channel and without invoking an Agent Runtime Adapter. The current application remains one Codex Runtime in `single-agent` mode. Live Worker dispatch, Supervisor Inbox delivery, current-ledger migration, renderer workflow, a second production endpoint, network transport, authentication, Access changes, and endpoint-snapshot reconciliation remain separate later slices.
